# デザイン検討のための資料

「れしぴょん（recipion）」の見た目（UI/UX）を決めるときに、デザインを考える人・AI へ渡すための資料。実装は別の担当（Claude Code）が、決まったデザインを反映する。
今の見た目は**仮**（機能の実装を優先したため、色と余白は最小限）。**振る舞いは、変えない前提**で、見た目と操作の手がかりを決めてほしい。

## 1. アプリの概要

日本語の家庭料理向けの Web アプリ（PWA。スマホが主、PC でも使う）。**買い物メモ・食材の在庫・レシピ**をつなぐ。

- 買い物メモに入れる → 買ったら在庫に入る → レシピの材料を在庫と比べる → 足りないものをメモに入れる → 作ったら在庫から引く、という循環。
- 買い物メモは、ログインなしでも使える（端末内に保存）。在庫とレシピは、ログインが要る。
- ログインは、メールに届く6桁のコードだけ（パスワードなし）。
- 表示名は「れしぴょん」。ドメインは recipion.app。UI の文言は、標準語の日本語（関西弁は使わない）。

## 2. 利用者と場面

- 料理をする人。**スーパーの店内（片手・立ったまま・電波が弱い）**と、**台所（手が濡れている・画面が遠い）**で使う場面が多い。
- そのため、**押す対象は大きく**、**一覧は素早く見渡せて**、**オフラインでも崩れない**ことを重視する。

## 3. 画面の一覧

| パス | 内容 | 補足 |
|---|---|---|
| `/` | 機能へのナビ | 入口 |
| `/shopping` | 買い物メモ | 一覧／店ごとの表示、チェック、並び替え（ドラッグ）、条件つきのメモ（「売っていたら…、なければ…」）、レシピから入れる、購入確定（期限の確認の画面つき） |
| `/inventory` | 在庫 | 食材ごとにロット（買った単位）を並べる。期限・保存方法、あり／なしだけの食材、単位の変更、数量の調整、登録フォーム |
| `/recipes` | レシピの一覧 | 自分のレシピ |
| `/recipes/new`・`/recipes/$id/edit` | レシピのエディタ | **入力欄は1つ**で、見出し（材料・下準備・作り方・メモ）で区切って書く。右（スマホではタブ）にプレビュー。補完メニュー、`[[…]]` で他のレシピへのリンク |
| `/recipes/$id` | レシピの参照 | 材料・作り方、買い物メモに入れる、「作った」（在庫から引く・元に戻す）、リンクのプレビュー（シート）、公開範囲、通報 |
| `/profile` | プロフィール | 表示名・ハンドル、退会 |
| `/terms`・`/privacy` | 利用規約・プライバシーポリシー | 長い文章 |
| `/admin/*` | 管理者の画面 | 運営者だけ。通報・申し立て・ユーザーの停止。一般の導線には出ない。見た目は、最小限の整理でよい |
| ログイン | メールアドレス → 6桁コード | コードは、1つの入力欄を、6つの枠に見せている（全角入力・貼り付けにも対応） |

## 4. デザインの原則（運営者の希望）

1. **アフォーダンスとシグニファイア**を強く意識する。押せる・入力できると、見て分かる形にする。操作の手がかりを、隠さない。
2. **シンプルでおしゃれ**。参考：nani.now、zenn.dev。
3. **色はイエロー系**（淡いオレンジなど）が今の案。**決めるのは運営者**（候補を複数見せて、一緒に決める）。
4. **非同期のボタンは変形する**：押すと、その場でスピナーに変わり、終わったらチェックに変わる（失敗の状態も）。保存・送信・削除の確認・通報・申し立てなど、全般に使う。→ 共通のボタン部品（待機・処理中・完了・失敗）として設計する。処理中は押せない（二重送信の防止）。状態は読み上げでも分かる（`aria-busy` など）。
5. 色だけに頼らない（色覚の違い、屋外の明るさ）。コントラストを十分に取る。ダークモードは、今は未対応（必要か、提案がほしい）。

## 5. 特に、デザインが要る部品

- **ボタンの共通部品**（上の4）。主・副・危険（削除、停止）・無効、の区別。
- **数量の入力**：分数（1/2、1と1/2）に対応。単位ごとに、押しやすいボタンが並ぶ（玉・株は 1/4・1/3・1/2・3/4、g は +10・+50・+100…）。
- **補完メニュー**（レシピのエディタ）：カーソルの近くに出る縦の一覧（PC）／キーボードの上の横の帯（スマホ）。日本語の変換候補の窓と重ならない配慮がある。
- **プレビューのシート**：リンク先のレシピを、読み取り専用で見せる。スマホは下から出るシート、PC は中央の枠。
- **在庫のロット表示**：食材 → ロット（数量・期限・保存方法）。期限が近い・切れた、の見せ方。
- **買い物メモの項目**：チェック、数量と単位、売り場（カテゴリ）、店、換算の補足、並び替えのつまみ。
- **条件つきのメモ**：「<材料>が<どんな時>」と、「そうなら／そうでなければ」の2つのまとまり。
- **空の状態・読み込み中・失敗**の見せ方（オフライン時を含む）。
- **文言のトーン**：やさしく、短く、標準語。

## 6. 技術上の制約（実装側との約束）

- スタイルは **vanilla-extract**（`*.css.ts`）＋ destyle.css（リセット）。色の基準は `src/styles.css` の CSS 変数（`--color-text`・`--color-surface`・`--color-primary` など）。**デザインは、まず「トークン」（色・文字・余白・角丸・影・動き）として決めてもらえると、実装が早い。**
- React 19。ブラウザだけで描画する画面と、サーバーで描画する画面がある。画面の初回表示は速く保つ（重い画像・Web フォントは、慎重に）。
- **オフラインで動く**（PWA）。外部のフォント・画像・スクリプトを新しく足すときは、先に相談する（プリキャッシュとの兼ね合い）。
- ブラウザの対象：Chrome・Safari・Edge。日本語の入力（IME）の変換中の挙動に配慮した部品がある（見た目を変えても、変換中のクリック・補完の位置が崩れないこと）。
- アイコンは `public/recipion-icon.svg`、PWA の `theme_color` / `background_color` は `public/manifest.webmanifest`。テーマの色が決まったら、合わせて直す。

## 7. デザインの成果物として、ほしいもの

1. **トークン一覧**（色：主・副・背景・文字・境界・状態（成功・警告・エラー）／文字の大きさと太さ／余白の段階／角丸／影／動きの長さと曲線）。ライトモードの値。
2. **共通部品の仕様**：ボタン（状態つき）、入力欄、チェック、タグ（期限・店・カテゴリ）、シート／ダイアログ、メニュー、リスト項目、空の状態。
3. **主要画面のレイアウト案**（スマホを先に、次に PC）：買い物メモ、在庫、レシピの参照、レシピのエディタ、ホーム、ログイン。
4. 文言の方針（トーン）と、アイコンの方針。

画像（モックアップ）だけでなく、**数値と理由が読める形（文章・表）**で渡してほしい。実装側が、そのまま反映できるように。

## 8. 変えないでほしいこと（振る舞い）

- 画面の機能、データの扱い、入力の規則、権限の判定。
- レシピのエディタが「入力欄1つ＋見出しで区切る」こと。
- 在庫の単位と、買い物メモの単位が、別の役割であること（在庫は食材ごとの決まった単位、メモは自由な単位）。
- 管理者の画面が、一般の導線に出ないこと。

見た目の都合で、これらを変えたほうがよいと思うときは、**変えずに、提案として別に書いてほしい**。

## 9. 追記（2026-10-13）：デザイン案の反映が進んだ段階での、追加の依頼

実装側で、デザイントークン（`src/styles.css`）、マスコット「れしぽよ」、アニメーション付きボタンまでを反映した。その過程で、**共通の部品として仕様が必要なもの**と、**ボタンについて、仕様の判断が要る点**が見つかった。

### 9.1 ボタンについて、判断してほしい点（実装は、次の方針で反映済み／保留）

実装済み：処理中だけ押せない（完了・失敗の表示中は、続けて押せる。続けて登録する場面で、待たされないため）。小さいボタン（sm）は 40px。

**方針（運営者）：画面に、見える文字を足しすぎない。** ごちゃごちゃさせない。ただし、読み上げのための文は、見えなくても入れる（アクセシビリティは別）。見える文字は、本当に必要なときだけにし、できるだけ、形・位置・動き・アイコンで伝える。

判断・仕様が要るもの：
1. **無効のボタンの理由の見せ方**。いまは灰色になるだけで、なぜ押せないのかが分からない（例：メールが空で「コードを送る」が押せない）。**常時は文字を出さず**、押そうとしたとき（タップ・hover・フォーカス）にだけ出す、または、入力欄の側で「ここが足りない」と分かる形（例：未入力の欄に、目立つ印）にする案がほしい。
2. **押せる範囲と見た目の大きさ**。小さいボタンも、押せる範囲は 44px 以上にしたい（店内の片手操作）。見た目が小さいままにするなら、押せる範囲の広げ方の指定がほしい。
3. **ghost（枠も背景もない、文字だけのボタン）を使うか**。いまのアプリでは、まだ使っていない。ふつうの文字と区別がつかず、押せると分かりにくい。使うなら、場面の限定（閉じる・やめる など）と、手がかり（下線・アイコン・hover）を決めてほしい。使わないなら、種類から外す。
4. **れしぽよのコントラスト**。白地の上で、黄色の体のコントラストが約 2:1（非文字の目安は 3:1）。体の縁の色・太さ、または体の色の指定がほしい。
5. **処理が長引いたとき**（目安 3 秒以上）の表現。文字を足さずに、れしぽよの動き・表情の変化で、「時間がかかっている」と伝えられないか、提案がほしい。
6. **失敗したとき**、ボタンは短い文言（「失敗しました」）を出す。理由は、原因の場所（入力欄の下など）の文で出している。ボタンの文言は、アイコンだけにして、文字を省けるかも含めて、方針がほしい。
7. **広がったときの隣の要素**。横並びの行では、完了の文言で広がると、隣が押される。許容か、文言を省くか（チェックだけにする）の方針がほしい。

### 9.2 追加で必要な共通部品（実装済みのコードの繰り返しの数を根拠に、優先順）

仕様は、**状態ごと**（通常・hover・押下・フォーカス・無効（理由つき）・エラー・処理中）と、**押せる範囲（44px 以上）**、**色だけに頼らないこと**、**非文字のコントラスト（3:1 以上）**を含めてほしい。

| 優先 | 部品 | いまの状態（根拠） |
|---|---|---|
| 高 | **入力欄のまとまり**：ラベル・補足・エラー・必須/任意。テキスト・複数行・選択・チェック・ラジオ | `label` 55、`input` 46、`select` 15、エラー文 33。見た目・エラーの出し方が、ファイルごとに違う |
| 高 | **お知らせの文**：情報・成功・警告・エラー（アイコン＋色＋文）。入力欄の下の短い文と、画面の上の帯の2種類 | エラー 33、状態 14。色だけの箇所がある |
| 高 | **確認のダイアログ**：元に戻せない操作（削除、停止、アカウントの削除、作り直し） | 約 7 か所に、別々の作りの2段階の確認がある |
| 高 | **チップ/タグ**：期限・店・カテゴリ・保存方法。選べる版（押した状態つき） | プリセット、クイック期限、数量、並び替えなど |
| 高 | **アイコンボタン**：並び替え、編集、削除、閉じる（見えないラベル、短い説明つき） | 買い物メモと在庫の行に多数 |
| 中 | **カード/行**：買い物の項目、在庫の食材、レシピの行（先頭にチェック、後ろに操作） | `li` 43、見出し 24 |
| 中 | **空の状態**：説明＋次の操作＋れしぽよ | 「まだ…/ありません」29 か所 |
| 中 | **読み込み中／失敗（やり直しつき）** | 「読み込み」34 か所。文字だけ |
| 中 | **画面の枠とナビ**：タイトル、戻る、最大幅、スマホの下部ナビ | リンク 32 か所 |
| 中 | **シート／中央の枠** | リンク先のプレビュー、期限の確認など |
| 低〜中 | タブ/切り替え、オフライン・同期のバナー | 3 か所以上／別々に出ている |
| 低 | 取り消しの通知（「元に戻す」つき）、折りたたみ | 「作った」のあとなど |

### 9.3 部品の背景にある、主な操作・流れ

1. 入力 → 確認 → 送信 → 結果（フォーム）　2. 元に戻せない操作の確認　3. 取り消せる操作（作った → 元に戻す）　4. 一覧の項目の操作（チェック、並び替え、編集、削除）　5. 選ぶ（単位、店、保存方法、公開範囲）　6. 空・読み込み中・失敗・オフライン　7. プレビューを見る → 戻る　8. 未ログインから、ログインへ誘う　9. 停止・権限・エラーの画面　10. 長い文章を読む（規約）　11. 管理者の一覧と操作（最小限でよい）

### 9.4 マスコット「れしぽよ」を使う場所（提案）

ボタンの処理中のほか、空の状態、読み込み中、オフライン、エラー画面。**表情の変化（通常・読み込み中・うれしい・かなしい）を、将来の実装の候補にしている**（今回は未実装）。使う場所と、表情の仕様もあわせて、提案がほしい。
